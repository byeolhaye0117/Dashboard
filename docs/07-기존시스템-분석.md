# 기존 시스템 분석 — good-fitness.vercel.app

- 대상: https://good-fitness.vercel.app (MTO 피트니스 / GOOD FITNESS 업무 관리 시스템)
- 분석일: 2026-07-29
- 방법: 공개된 웹페이지와 공개 API 응답 확인 (로그인하지 않은 상태)

> 확인 과정에서 회원·직원의 실제 개인정보 **값은 출력하지 않았습니다.**
> 항목 이름과 건수만 확인했습니다.

# 1. 보안 점검 결과 — 즉시 조치 필요

## 1-1. 무엇을 확인했나

로그인을 하지 않은 상태에서, 브라우저 주소창에 주소만 입력해 아래 정보를 받을 수 있었습니다.

| 주소 | 결과 | 내용 |
|---|---|---|
| `/api/staff?branch=쌍용점` | 열림 | 직원 10명 — 이름 · 전화번호 · 직급 · **비밀번호** |
| `/api/registration?branch=쌍용점` | 열림 | 등록·결제 **182건** — 회원명 · 결제금액 · 미수금 · 나이대 · 거주지역 |
| `/api/consultation?branch=쌍용점` | 열림 | 상담 **61건** — 이름 · **전화번호** · 문의내용 |
| `/api/bipum?branch=쌍용점` | 열림 | 비품 44건 |

## 1-2. 왜 이렇게 되었나

로그인 검사가 **직원 브라우저 안에서** 이루어지고 있습니다.

```
현재 방식
  ① 브라우저가 서버에 요청: "쌍용점 직원 목록 주세요"
  ② 서버가 응답: 이름·직급·전화번호·비밀번호 (전원 분)   ← 여기가 문제
  ③ 브라우저가 검사: 입력한 비번 == 받아온 비번 ?
  ④ 맞으면 localStorage에 로그인 표시를 남기고 통과
```

②에서 **비밀번호가 이미 브라우저로 넘어옵니다.**
③의 검사는 그 뒤에 일어나므로, 검사를 통과하지 않아도 정보는 이미 손에 들어와 있습니다.

## 1-3. 실제로 가능한 일

1. **주소만 알면 누구나** 직원 전원의 이름·전화번호·비밀번호를 볼 수 있습니다.
2. 알아낸 비밀번호로 **아무 직원 계정으로나 로그인**할 수 있습니다.
3. 로그인 표시(`localStorage`의 `mto_login`)를 직접 만들어 넣으면 **비밀번호 없이도** 들어갈 수 있습니다.
4. 회원 182명의 결제 내역과 상담 61건의 **이름·전화번호**가 그대로 노출됩니다.

## 1-4. 법적으로 문제가 되는 부분

회원의 이름과 전화번호는 개인정보보호법상 **개인정보**입니다.
정보를 지킬 안전조치 없이 외부에서 접근 가능한 상태이면 관리 책임 문제가 생길 수 있습니다.

## 1-5. 조치 방안

| 방안 | 소요 | 효과 | 업무 영향 |
|---|---|---|---|
| **① 사이트를 잠시 닫기** | 즉시 | 완전 차단 | 직원들이 업무를 못 함 |
| **② 비밀번호를 응답에서 빼고 서버에서 검사** | 반나절 | 핵심 구멍 막힘 | 없음 |
| **③ 모든 API에 로그인 확인 붙이기** | 1~2일 | 완전 해결 | 없음 |
| **④ 새 대시보드로 옮기기** | 개발 기간 | 완전 해결 | 없음 |

**권장 순서: ② → ③ → ④**
②만 해도 가장 큰 구멍은 막힙니다. ④는 어차피 진행할 일이니 그때까지 ②③으로 버팁니다.

조치하려면 `good-fitness` 저장소에 접근할 수 있어야 합니다.

# 2. 기존 시스템에서 확인한 기능

## 2-1. 로그인 방식

```
지점 선택  ▼  →  직원 선택  ▼  →  비밀번호 입력  →  로그인
```

**이 방식은 그대로 가져갑니다.** 헬스장 직원에게 매우 잘 맞습니다.
- 아이디를 외울 필요가 없음
- 이름을 목록에서 고르기만 하면 됨
- 재직중인 직원만 목록에 뜸

## 2-2. 만들어져 있는 기능 (API 기준)

| 기능 | 주소 | 내용 |
|---|---|---|
| 직원 | `/api/staff` | 지점별 직원 목록, 재직 상태 |
| 등록·매출 | `/api/registration` | 회원 등록과 결제 |
| 상담 | `/api/consultation` | 문의 접수, 약속 전환 |
| 출퇴근 | `/api/attendance` | 출근·퇴근 기록 |
| 배정업무 | `/api/assigned` | 직원에게 배정된 일 |
| 반복업무 | `/api/routine` | 매일·매주 반복되는 일 |
| 긴급업무 | `/api/urgent` | 급한 일 |
| 문제점 발굴 | `/api/problem` | 문제 발견 → 해결 추적 |
| 주문요청 | `/api/order` | 물품 주문 요청 |
| 비품관리 | `/api/bipum` | 비품 재고 (충분/보통/부족) |
| 예약 동기화 | `/api/sync-appointments` | 상담 약속 반영 |

데이터는 **노션(Notion)** 에 저장되고 있습니다.

## 2-3. 이미 정해져 있던 항목들 (그대로 씁니다)

### 등록·매출 입력 항목

```
회원명 · 회원권명 · 등록개월수 · 회차 · 담당 트레이너
매출유형 · 결제유형 (현금 / 카드 / 계좌 / 카드+계좌)
계약금 · 총 결제 금액 · 미수금 · 미수금 결제예정일
현금영수증 · 락커 번호 · 서비스 항목 · 기타매출 · 기타상품명
신규회원 / 재등록회원 · 초대권 발급 · 메모
```

### 상담 입력 항목

```
상담날짜 · 문의날짜 · 이름 · 전화번호 · 성별 · 나이대
문의 유형 · 문의내용 · 상담자 · 접수자
방문경로 · 거주동네 · 직업
약속 일시 · 약속전환 · 예약확정 · 등록여부 · 미등록 사유
```

### 이미 쓰고 계신 분류값 — 새로 정할 필요 없음

| 구분 | 항목 |
|---|---|
| **방문경로** | 네이버 · 인스타 · 카카오톡 · 지인추천 · 문자 · 전화 · 간판 · 직접 |
| **거주동네** | 봉명동 · 불당동 · 성정동 · 신부동 · 쌍정동 |
| **직업** | 직장인 · 자영업 · 자유업 · 학생 · 의료직종 · 프리랜서 |
| **결제유형** | 현금 · 카드 · 계좌 · 카드+계좌 |
| **비품 상태** | 충분 · 보통 · 부족 |
| **문제 해결상태** | 해결전 · 해결중 · 해결완료 |

### 이미 보고 계신 지표

- 오늘의 업무 성취율
- 주간 상담예약 / 주간 약속전환
- 우선순위, 목표횟수

# 3. 새로 알게 된 업무 (기존 기획서에 없던 것)

| 업무 | 설명 | 기획서 반영 |
|---|---|---|
| **문제점 발굴** | 직원이 문제를 발견 → 해결전/해결중/해결완료 추적. 해결 후 모습 기록 | 새로 추가 필요 |
| **주문요청** | 필요한 물품을 직원이 요청 | 재고 모듈에 통합 |
| **업무 3종 분리** | 배정업무 / 반복업무 / 긴급업무를 나눠서 관리 | 체크리스트 모듈 확장 |
| **약속 전환 관리** | 상담 → 방문약속 → 예약확정 → 등록 단계 추적 | 상담 모듈에 반영 |
| **초대권 발급** | 등록 시 초대권을 주는 제도 | 새로 추가 필요 |
| **락커 번호 배정** | 등록 시 락커 번호를 지정 | 회원 항목에 추가 |
| **현금영수증 발행 여부** | 결제 시 기록 | 결제 항목에 추가 |

# 4. 기존 시스템과 새 자료의 차이

| 항목 | 기존 사이트 | 엑셀 자료 | 확인 필요 |
|---|---|---|---|
| 지점 | 쌍용 · 성정 · 용곡 (**3개**) | 쌍용 · 성정 · 용곡 · **두정** (4개) | 두정점을 추가해야 하는가 |
| 신항점 | 코드에 흔적 있음 | 없음 | 없어진 지점인가 |
| 직원 | 쌍용점 10명 | 쌍용점 8명 | 어느 쪽이 최신인가 |
| 비밀번호 | 10명 중 5명만 설정됨 | — | 나머지 5명은 로그인 불가 상태 |

# 5. 결론

## 그대로 가져갈 것

- 지점 → 직원 → 비밀번호 순서의 **로그인 화면**
- 등록·매출 / 상담의 **입력 항목 전부**
- 방문경로 · 거주동네 · 직업 등 **분류값 전부**
- 문제점 발굴 · 주문요청 · 업무 3종 분리 등 **실제 운영 중인 업무 흐름**

## 반드시 고칠 것

- 로그인 검사를 **서버에서** 하도록 변경
- 비밀번호를 **암호화해서 저장**
- 모든 API에 **로그인·권한 확인** 추가
- 직급별로 **볼 수 있는 데이터 자체를 제한**

## 다시 판단할 것

- 노션을 계속 데이터 저장소로 쓸 것인가
  - 지금 규모(등록 182건)에서는 문제없음
  - 4개 지점 · 회원 수천 명으로 커지면 속도 문제가 생김
  - 노션 자체가 원인이 아니라 **로그인 처리 위치**가 문제였음
