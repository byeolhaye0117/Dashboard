# 데이터 구조 (v1) — 무엇을, 왜 이렇게 저장하는가

실제 스키마: `supabase/migrations/0001_init.sql`
검증 시나리오: `supabase/tests/scenario_test.sql`

이 문서는 **개발자가 아니어도 읽을 수 있게** 쓴 설명입니다.
"이 표에 뭐가 들어가고, 왜 이렇게 나눴는가"만 다룹니다.

---

## 0. 확정된 요구사항

| 항목 | 결정 |
|---|---|
| 정지(홀딩) | **필요** — 기간만큼 만료일 자동 연장 |
| 양도 | **필요** — A회원 → B회원 계약 이전 |
| 환불·부분환불 | **필요** — 기록을 남기고 매출에서 차감 |
| 락커·운동복 | **따로 파는 상품** — 자체 기간과 만료일을 가짐 |
| 출입 기록 | 브로제이 사용 중 → **연동 대비해 자리만 마련** |

---

## 1. 전체 그림

```
지점 ─┬─ 직원 (관장 / 매니저 / 데스크 / 트레이너)
      ├─ 상품 (3개월권, PT 20회, 락커 3개월 …)
      ├─ 상담 ──────────────┐
      └─ 회원 ←─────────────┘ 등록으로 전환되면 회원이 됨
            └─ 계약 (= 등록 1건)
                 ├─ 정지 기록      → 만료일이 자동으로 밀림
                 ├─ 양도 기록      → 다른 회원에게 넘김
                 ├─ 결제 / 환불    → 매출
                 └─ PT 세션 기록   → 트레이너 실적, 잔여 횟수
```

총 13개 표. 이 중 관장님이 실제로 신경 쓸 건 **회원 / 계약 / 결제 / PT세션 / 상담** 5개입니다.
나머지는 기록용이거나 설정용입니다.

---

## 2. 표 하나씩

### 지점 (`branches`)
지점명, 코드(강남=GN), 주소, 전화, 오픈일.
지점을 지우는 대신 **비활성 처리**합니다. 폐점해도 과거 매출은 남아야 하니까요.

### 직원 (`staff`)
이름, 역할, 소속 지점, 재직 여부.

역할은 4가지입니다.

| 역할 | 볼 수 있는 범위 | 할 수 있는 일 |
|---|---|---|
| `owner` 관장 | **전 지점** | 전부 |
| `manager` 매니저 | 자기 지점 | 회원·결제 입력, 상품 관리 |
| `desk` 데스크 | 자기 지점 | 회원·결제·상담 입력 |
| `trainer` 트레이너 | 자기 지점 | **PT 세션 체크만** (결제는 못 건드림) |

> 소속 지점이 비어 있으면 본사 계정으로 보고 전 지점을 볼 수 있습니다.

### 상품 (`products`)
이름, 종류, 기간 또는 횟수, 정가.

**종류가 4가지뿐인 게 핵심입니다.**

- `membership` 기간제 회원권 → 90일, 180일 …
- `pt` PT 횟수권 → 10회, 20회 …
- `group` 그룹수업 (GX, 필라테스 등)
- `addon` 부가상품 (락커, 운동복)

새 상품이 생겨도 **표 구조를 바꾸지 않습니다.** 설정 화면에서 한 줄 추가하면 끝입니다.
"6개월권 추가", "PT 30회 신설", "여름 특가 3개월" 전부 데이터만 넣으면 됩니다.

### 회원 (`members`)
이름, 연락처, 성별, **생년(연도만)**, 유입경로, 최초 등록일.

주민번호·주소는 **일부러 받지 않습니다.** 헬스장 운영에 필요 없는데
유출되면 책임만 커집니다.

회원이 개인정보 삭제를 요청하면 이름·연락처만 지우고 `파기 시각`을 남깁니다.
→ **과거 매출 통계는 그대로 유지됩니다.** (검증 완료)

### 계약 (`contracts`) — 가장 중요한 표
"이 회원이, 이 상품을, 언제부터 언제까지, 얼마에" 를 담습니다.

만료일이 **두 개**인 게 이 표의 핵심입니다.

| 칸 | 뜻 |
|---|---|
| `base_ends_on` | 정지를 반영하지 않은 **원래** 만료일 |
| `ends_on` | 정지 일수를 더한 **실제** 만료일 ← 화면에 보이는 값 |

왜 나눴느냐면, 정지가 여러 번 들어오거나 나중에 취소될 수 있기 때문입니다.
원래 날짜를 안 갖고 있으면 두 번째 정지부터 계산이 어긋납니다.

**잔여 횟수는 저장하지 않고 계산합니다.** (총 횟수 − 사용 횟수)
두 군데 저장하면 언젠가 반드시 어긋나고, 어긋나면 회원과 분쟁이 납니다.

### 정지 (`contract_holds`)
시작일, 종료일, 사유.

정지 기록을 넣거나 고치거나 지우면 **만료일이 자동으로 다시 계산됩니다.**
직원이 날짜 계산을 할 일이 없습니다.

> 2/1~2/15 정지(15일) → 만료일 4/1 이 4/16 으로 자동 연장.
> 정지를 취소하면 4/1 로 자동 원복. (둘 다 검증 완료)

진행 중인 정지(복귀일 미정)도 지원합니다. 오늘까지로 계산하다가,
복귀 처리하는 순간 확정됩니다.

### 양도 (`contract_transfers`)
누가 → 누구에게, 언제, 수수료 얼마, 넘길 당시 잔여 기간/횟수.

원 계약은 `양도됨` 상태로 닫고 양수인 이름으로 새 계약을 만듭니다.
→ **양도한 사람은 만료 임박 연락 목록에서 빠집니다.** (검증 완료)
이걸 안 해두면 이미 넘긴 회원한테 재등록 전화를 겁니다.

### 결제 (`payments`)
계약, 금액, 결제일, 결제수단, 분할 회차.

**계약과 결제를 나눈 이유**
33만원 회원권을 1월에 20만, 2월에 13만 받았다면 —
합쳐서 저장하면 1월 매출이 33만으로 잡혀 틀립니다.
나눠 저장하면 1월 20만 / 2월 13만으로 정확히 갈립니다. (검증 완료)

**환불은 지우지 않고 음수로 남깁니다**
140만 결제 후 50만 환불 → 기록 2줄, 실매출 90만.
- 원본이 남아 분쟁 시 근거가 됩니다
- "지난달 매출이 왜 바뀌었지?"가 생기지 않습니다
- 환불을 실수로 양수로 넣으면 **DB가 거부합니다** (검증 완료)

### PT 세션 (`pt_sessions`)
계약, 트레이너, 일시, 상태(진행/노쇼/취소), 차감 여부.

**1회 진행 = 1줄.** 잔여 횟수만 깎지 않는 이유는,
그러면 "이번 달 누가 몇 회 뛰었나", "노쇼가 잦은 회원은 누구인가"를
영영 알 수 없기 때문입니다.

노쇼 차감 여부를 켜고 끌 수 있습니다. 나중에 봐주기로 하면
체크만 풀면 잔여 횟수가 자동으로 되돌아옵니다. (검증 완료)

### 상담 (`consultations`)
이름, 연락처, 유입경로, 상담일, 상담자, 결과, 재연락일.

결과는 `대기 / 등록 / 보류 / 이탈` 4가지.
등록으로 바뀌면 어느 회원이 됐는지 연결됩니다 → **전환율이 나옵니다.**
보류 고객은 재연락일을 잡아두면 그날 할 일 목록에 뜹니다.

### 출입 (`check_ins`)
지금은 **비어 있는 표**입니다. 브로제이 연동이 확정되면 채웁니다.
미리 만들어두는 비용은 0원이고, 나중에 붙이기가 훨씬 쉬워집니다.

### 변경 이력 (`audit_logs`)
누가 언제 무엇을 고쳤는지. 관장만 볼 수 있습니다.

## 3. 화면 없이도 바로 나오는 숫자들

DB에 미리 만들어 둔 조회식입니다. 화면은 이걸 가져다 그리기만 하면 됩니다.

| 이름 | 답하는 질문 |
|---|---|
| `v_monthly_revenue` | 지점별·월별·상품종류별 매출 (환불 자동 차감) |
| `v_expiring_contracts` | 30일 내 만료 회원 + 연락처 + 남은 일수 |
| `v_low_session_contracts` | 잔여 2회 이하 PT 회원 (재결제 시점) |
| `v_consultation_conversion` | 지점별·월별 상담 건수와 전환율 |
| `v_trainer_sessions` | 트레이너별 월간 진행/노쇼/취소 횟수 |

## 4. 지점 격리는 DB가 강제합니다

"강남점 직원은 강남점만 본다"를 **앱 코드가 아니라 DB가** 막습니다.

앱에서 실수로 전체 조회를 날려도 DB가 자기 지점 것만 돌려줍니다.
다지점 운영에서 이건 타협할 수 없는 부분이라 이렇게 잡았습니다.

기본 정책은 아래와 같고, 바꾸고 싶으면 말씀만 하시면 됩니다.

- 관장 → 전 지점
- 매니저·데스크 → 자기 지점만
- 트레이너 → 자기 지점, PT 세션만 입력 가능

## 5. 검증 결과

`supabase/tests/scenario_test.sql` 을 실제 PostgreSQL 16에 돌려
아래 10개 시나리오 · 15개 검증이 모두 통과했습니다.

1. 정지 15일 → 만료일 자동 연장 / 정지 취소 → 원복
2. 분할결제 → 월별 매출 정확히 분리
3. 부분환불 → 실매출 차감 + 원본 보존 + 부호 오입력 차단
4. PT 세션 → 사용·잔여 자동 계산 / 노쇼 정정 / 초과 사용 차단
5. 만료 임박·소진 임박 목록에 정확히 잡힘
6. 상담 전환율 계산
7. 양도 → 원 계약이 연락 목록에서 빠짐
8. 개인정보 파기 후에도 매출 통계 유지
9. 지점별 매출이 섞이지 않음
10. 외부 시스템 중복 유입 차단

테스트가 형식적이지 않다는 것도 확인했습니다 —
만료일 계산에 하루 오차를 일부러 심었더니 테스트가 잡아냈습니다.

## 6. 다음에 정해야 할 것

1. **브로제이 연동 여부** — 아래 별도 항목 참고. 이게 가장 중요합니다.
2. 실제 판매 중인 상품명·가격 (설정 초기값으로 넣을 것)
3. 지점 이름과 개수
4. 노쇼 차감 정책 (기본은 차감함)
5. 트레이너가 직접 세션 체크할지, 데스크가 대신할지

### 브로제이에 대해

브로제이는 출입 장치가 아니라 **회원관리 CRM 전체**를 제공하는 서비스로 확인됐습니다.
매출 통계, 다지점 통합 관리, 정기결제까지 포함돼 있습니다.

그렇다면 이 대시보드가 취할 수 있는 길은 둘입니다.

| 방향 | 내용 | 위험 |
|---|---|---|
| **A. 우리가 원본** | 직원이 이 대시보드에 입력. 브로제이는 출입만. | 브로제이에도 회원을 넣어야 문이 열린다면 **이중 입력**이 됩니다. 대시보드가 죽는 가장 흔한 원인입니다. |
| **B. 브로제이가 원본** | 브로제이 데이터를 가져와 보여주고, 부족한 것(상담·마케팅 성과)만 여기서 입력. | 브로제이가 데이터를 내주는지에 달렸습니다. |

**확인해주셔야 할 것:** 브로제이 고객센터에 딱 두 가지만 물어봐 주세요.

> 1. 회원·결제 데이터를 **엑셀로 내려받을 수** 있나요?
> 2. **API로 데이터를 가져갈 수** 있나요? (개발사 연동 지원 여부)

답에 따라 방향이 갈립니다.

- **API 됨** → B안. 자동 동기화. 이중 입력 없음. **가장 좋습니다.**
- **엑셀만 됨** → B안 변형. 월 1~2회 엑셀 업로드 + 상담·마케팅은 직접 입력.
- **둘 다 안 됨** → A안. 단, 브로제이 쪽 입력은 최소한(출입용 이름·만료일)만 하고
  나머지는 여기서 관리하도록 업무를 나눠야 합니다.

**어느 쪽이든 지금 만든 데이터 구조는 그대로 씁니다.** 모든 표에
`source`(어디서 왔는지)와 `external_ref`(브로제이 쪽 ID)를 미리 넣어뒀고,
같은 데이터가 두 번 들어오는 것을 DB가 막는 것까지 검증했습니다.
그래서 이 확인을 기다리느라 작업이 멈추지는 않습니다.
